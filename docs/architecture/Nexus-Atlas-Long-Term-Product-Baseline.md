# Nexus Atlas Long-term Product Baseline v0.1

## 1. Non-negotiable Product Direction

Nexus Atlas remains a **Personal Intelligence Infrastructure**. The competition validates one vertical slice; it does not redefine the product as a Verity assistant, competition tool, or Re-entry-only application.

```text
Personal Intelligence Infrastructure
  → Nexus Atlas
  → Context Fabric + Context Projections + Intelligence Services
  → Territory Views
  → Workspaces, Agents, Records, Decisions, Actions
```

## 2. Permanent Layers

All layers are designed as a complete product system now. Implementation depth may differ, but no layer is removed for the competition.

### Layer A — Source Layer
GitHub, DataHub, Notion, Drive, files, direct user input, agent outputs.

### Layer B — Context Fabric
Provider-neutral primitives:
- Person
- Project
- Record
- Event
- Decision
- Goal
- Action
- AgentRun
- ExternalAssetRef
- Relationship
- Provenance and State

### Layer C — Context Projections
- Identity Context
- Knowledge Context
- Memory Context
- Decision Context
- Action Context

These are dynamic views over the same Context Fabric, not separate databases.

### Layer D — Intelligence Services
- Context Builder
- Continuity Engine
- Decision Trace
- Conflict Resolution
- Action Engine
- Context Policy and governed mutation

### Layer E — Capability / Agent Layer
Research, writing, evaluation, planning, review, and specialized capabilities such as Inkraft, PrismAI, and Verity.

### Layer F — Experience Layer
- Atlas Desk
- Atlas Map
- Territory Index
- Territory Workspace
- Record / Decision / Asset detail
- Agent Workspace
- Action Tray
- Context Inspector
- Connector and Policy Center

## 4. Territory Contract

A Territory is a **view and working mode**, not a database.

Each Territory configures:
- prioritized Context projections;
- relevant relation types;
- capabilities and agents;
- default Workspace templates;
- action classes and review rules.

The same entity may appear in several Territories. Verity belongs primarily to Innovation and secondarily to Evaluation.

## 5. Complete Design vs Implementation Depth

| Product area | Design commitment now | Competition implementation | Long-term implementation |
|---|---|---|---|
| Atlas Desk | Full information architecture and visual system | Functional Verity re-entry entry point | Multi-project prioritization and personal route |
| Atlas Map | Full relationship language and interaction model | Functional Verity project-focus map | Cross-project and cross-Territory exploration |
| Innovation Territory | Full Territory shell | Deep Verity vertical slice | Multiple innovation projects and capabilities |
| Other Territories | Full page structure, projection rules, navigation | Visible but not fake-functional | Implement one by one using shared Context Fabric |
| Context Inspector | Full shared component | Fully functional for Demo entities | Universal provenance, rules, and audit |
| Agent Workspace | Full contract and navigation | Conflict resolution + Context Package handoff | Multiple specialized agents/capabilities |
| Sources/Policies | Full model | DataHub read and one governed write | Additional connectors and user-managed policies |

“Full design” does **not** mean pretending unfinished Territories work. It means the permanent product architecture, navigation, component system, and contracts are established, while unfinished functions are honestly marked as future capabilities.

## 6. Design Language

**Archive Cartography** is the permanent design direction.

It should feel like a contemporary working atlas:
- structured indexes;
- mapped routes;
- field annotations;
- archival provenance;
- restrained material texture;
- analytical instruments.

It must not regress to:
- Star Map;
- cosmic or sci-fi metaphors;
- neon graph visualizations;
- generic AI dashboards;
- a gallery of disconnected tool cards.

## 7. Competition Guardrails

The competition may:
- deepen one Territory;
- use one project;
- implement one governed DataHub mutation;
- limit data volume;
- record a focused three-minute path.

The competition may not:
- rename Nexus around Verity;
- make Verity-specific fields core primitives;
- bypass Atlas Desk/Map/Workspace layers;
- create a separate competition database;
- make DataHub the sole source of truth for personal Context;
- claim incomplete Territories are functional;
- replace product architecture with a one-page Demo.

## 8. Post-competition Sequence

1. Stabilize provider-neutral Context Fabric and event/audit model.
2. Complete Atlas Desk multi-project state.
3. Generalize Project Re-entry beyond Verity.
4. Implement Atlas Map cross-project routes.
5. Add Learning Re-entry.
6. Add Research Re-entry.
7. Integrate Inkraft into Creation and PrismAI into Evaluation.
8. Expand Identity Context and cross-Territory action planning.
9. Add user-configurable source and mutation policies.

## 9. Product Test

Every future feature must pass:

1. Does it strengthen long-term context continuity?
2. Is it provider-neutral at the domain layer?
3. Can another Territory reuse it?
4. Does the user see provenance and state?
5. Does consequential mutation require appropriate human authority?
6. Will it still belong to Nexus after the competition?
